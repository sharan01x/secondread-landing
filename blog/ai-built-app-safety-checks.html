1. Hardcoded Secrets Are Your Biggest Risk

What You Might Find

Your AI-built app likely has passwords, API keys, or sensitive tokens baked right into the source code. These aren't documented anywhere—they're just sitting there in your secrets.env, .env files, or even JavaScript files, invisible until discovered by a real user or a security scanner.

Why This Is Dangerous

If a secret is hardcoded:

  • Anyone who inspects your website's network traffic can extract it
  • Your production database could be compromised
  • Users' data becomes exposed (and you become liable)
  • A single leaked credential can tank your entire app

AI coding tools don't inherently distinguish between dev secrets and production credentials. They generate code based on what they think you want, not what's secure.

How to Fix It

  1. Scan all .env and config files for API keys matching patterns like api_key=, secret=, password=
  2. Check for hardcoded tokens in environment variables (many tools bypass .gitignore without warning)
  3. Never commit secrets to version control—use a proper secret management system or encrypted configuration

2. Missing Error Handling Turns Bugs into Production Failures

What You Might Find

AI coding tools often generate "happy path" code—logic that works _when everything goes right_. But real-world apps crash when users provide edge-case inputs, slow networks hit, or external APIs temporarily malfunction.

Your Bolt or v0-built app might:

  • Crash when a user submits an unexpected form value
  • Freeze during network timeouts
  • Fail gracefully nowhere—and your whole app becomes unusable

Why This Is Dangerous

Every unhandled error without proper fallback will eventually trigger in production. Users don't understand "it crashed because the API returned 502." They'll leave, or worse—tell their friends. Customer acquisition cost tanks overnight when your app is fundamentally broken.

Founders often assume "my code works locally" means "it's ready for users." It doesn't. Local tests run on your machine with perfect dependencies and fast responses. Production is a different beast entirely.

How to Fix It

  1. Add try/catch blocks around all async operations
  2. Implement fallback behaviors for slow or failed network calls
  3. Gracefully degrade features (e.g., enable offline mode when the API disconnects)
  4. Set up error boundaries in your frontend so one failing component doesn't kill the whole app

3. No Input Validation Lets Every Malicious User In

What You Might Find

Your AI-built code likely trusts everything the user gives it. It takes string inputs as strings, numbers as numbers, and array data without verifying. There's no sanitization, no validation, no verification.

This means your forms accept anything you receive—and your database stores anything you trust.

Why This Is Dangerous

Without input validation:

  • Malicious actors can inject SQL through form fields
  • XSS (cross-site scripting) attacks become trivial
  • Database poisoning becomes a single-click away
  • Your authentication bypasses entire security layers

AI coding tools don't "know" inputs are malicious until it's too late. They're trained on millions of public code repositories—many littered with vulnerabilities.

How to Fix It

  1. Validate every user input against known acceptable formats
  2. Sanitize output before displaying it anywhere on your site
  3. Implement a content security policy via HTTP headers
  4. Use parameterized queries for all database interactions (never dynamic SQL strings)

4. Placeholder Code Means Your Features Are Broken

What You Might Find

You asked your AI to build "a login system" or "a payment processing feature." It generated placeholder code—stubs that look real but do nothing when you run them.

Your Bolt-generated app might have:

  • A form that submits but doesn't call any API
  • UI components that render but fail when you interact with them
  • Database schemas without actual connection logic
  • Placeholder functions like console.log("Placeholder payment")

Why This Is Dangerous

These aren't bugs—they're intentional gaps. The AI _thinks_ building the feature is complete, and it's not wrong in a technical sense: it _generated_ something that looks like what you asked for. But when your customers try to use those features? They crash silently, or worse—do absolutely nothing.

Users don't know the difference between "I didn't finish this because I'm lazy" and "This isn't done yet." To them, both mean "This app is broken," and trust evaporates instantly.

How to Fix It

  1. Run your codebase with actual user interactions—don't just test locally
  2. Check that every component actually connects to its intended backend
  3. Review generated code for placeholder strings (TODO, FIXME, example.com, placeholder)
  4. Confirm every form input calls a real API endpoint with expected responses

5. Insecure Authentication Leaves Your Users Vulnerable

What You Might Find

AI coding tools often generate authentication systems that look functional but fall apart under scrutiny. Common issues:

  • No password requirements enforcement: Passwords shorter than 8 characters, or lacking complexity
  • Missing CSRF protection: Anyone who can visit your site can modify any logged-in user's session
  • Weak hashing: Using MD5 or SHA1 for password storage (both instantly crackable)
  • Missing rate-limits: Brute force attacks become trivial

Why This Is Dangerous

Authentication is the gatekeeper of everything else. Compromise auth, and you've opened every other part of your application to attackers. Without proper security patterns:

  • Session fixation becomes possible
  • Account hijacking takes seconds instead of hours
  • User data is exposed immediately
  • You're liable for breaches caused by basic mistakes

And again—AI doesn't learn from best practices unless explicitly told _how_ to do it. It sees what's common in public repositories, and insecure patterns are everywhere online.

How to Fix It

  1. Implement proper password hashing (bcrypt or argon2)
  2. Require CSRF tokens for all state-changing actions
  3. Use HTTPS-only cookies with Secure, HttpOnly, and SameSite flags
  4. Add rate-limiting to login endpoints
  5. Use a proven authentication package instead of custom-built logic
