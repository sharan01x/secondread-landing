AI Code Security Best Practices: A Founder's Guide to Safe AI-Generated Code

14 min read · Updated August 2026

You built your app with an AI coding tool — Bolt, Lovable, Cursor, v0, Replit, Windsurf, or one of the dozen others. The app works. It looks good. Users can sign up, click around, and do things. You're ready to launch.

But here's the uncomfortable reality: the AI that wrote your code is very good at making things work and very bad at making them safe. These are different skills, and the gap between them is where founders get hurt.

This guide walks through AI code security best practices — the practical, non-technical steps every founder should take before launching an app built with AI tools. No security background required. No jargon. Just clear, actionable guidance based on the latest research and real-world vulnerability data.

Why this matters now

The data is stark. Veracode's 2026 GenAI Code Security Report found that 44% of AI code generation tasks introduced security vulnerabilities — and the security pass rate has stayed flat at roughly 56% despite rapid improvements in everything else. Georgia Tech's Vibe Security Radar tracked 74 CVEs directly attributed to AI coding tools, with 35 in March 2026 alone (up from 6 in January). A peer-reviewed audit found only 10.5% of vibe-coded apps were secure. Tenzai found 98% of AI-generated apps shipped without basic security controls. The problem isn't theoretical. It's measurable, it's growing, and it affects your app.

Best Practice 1: Treat Every Line of AI-Generated Code as Untrusted

The single most important mindset shift: AI-generated code is not vetted code. It looks correct, it compiles, it passes a linter — but looking correct and being correct are different things. A string-concatenated SQL query looks fine. A missing authorization check looks fine. An API route that accepts any input looks fine. All three can compromise your application.

What this means in practice Critical Mindset

Orca Security, Checkmarx, and Arnica — three leading AI code security firms — all independently arrived at the same first principle: treat AI output as untrusted input. The code your AI tool generates should go through the same review and security scanning you'd apply to code from an unknown contractor. Because that's effectively what it is: code from a source that has no accountability for its security.

This isn't about distrusting AI. It's about applying the same standard you'd apply to any code that enters your codebase from outside your team. You wouldn't merge a random GitHub pull request without reviewing it. AI-generated code deserves the same scrutiny — arguably more, because it arrives faster and in larger volumes than any human contributor could produce.

What to do: Before launching, review every API route, authentication check, and data-handling function in your codebase. If you can't read the code yourself (most founders using AI tools can't), get a plain-English audit that translates the findings into terms you can act on. The goal isn't to become a developer — it's to know whether your app is safe to launch.

Best Practice 2: Never Hardcode Secrets in Source Files

This is the most common vulnerability in AI-generated code, and it's the most damaging. When an AI tool writes code that connects to an external service — a database, an API, a payment processor — it frequently embeds the credentials directly in the source file. Your OPENAI_API_KEY, your database connection string, your Stripe secret key — all sitting in plain text in a file that gets committed to git.

What happens Critical

Once a secret is in your git history, removing it from the current version doesn't fix the problem. Anyone who gains read access to your repository — an employee, a contractor, a hacker — can search your git history and find every secret that was ever committed. Tools like trufflehog and git-secrets exist specifically because this happens so often.

In March 2026, a vibe-coded app leaked 1.5 million API keys because the founder shipped without a security review. That's not an edge case — it's the predictable outcome of launching AI-generated code that hasn't been audited for hardcoded credentials.

What to do:

  • Use environment variables (.env files) for all secrets, never hardcode them in source files
  • Add .env, config/local.json, and any credentials files to .gitignore so they never enter git
  • If a secret was already committed, rotate it immediately — don't assume removing it from the current code is enough
  • Run a secret scanner (gitleaks, detect-secrets, or trufflehog) across your entire git history, not just the current code

Best Practice 3: Validate Every Input on Every API Route

AI tools are excellent at generating API routes that work with normal inputs. They're terrible at generating API routes that reject malicious inputs. This is because validation requires anticipating what an attacker might send — and AI tools optimize for the happy path, not the attack path.

What happens High Risk

A typical AI-generated API route receives a request, reads the body, passes it to a database query, and returns the result. What's missing: no check that required fields exist, no type validation (is email actually an email?), no length limits (what if someone sends a 50MB payload?), no sanitisation (could username contain a script tag?), and no rate limiting.

The result: SQL injection (attackers can read or modify your database), cross-site scripting (attackers can inject malicious scripts), denial of service (attackers can crash your app with oversized payloads), and data corruption (unexpected input types cause crashes or data loss).

What to do: Every endpoint that accepts external input — API routes, form handlers, webhook receivers — should validate input against a schema before processing. Use a validation library: Zod for TypeScript/JavaScript, Pydantic for Python, Joi for Node.js. Reject anything that doesn't match the expected shape. Add rate limiting to public endpoints. This is the minimum bar for a production API — there is no acceptable shortcut.

Best Practice 4: Verify Every Dependency the AI Added

AI coding tools add dependencies automatically. If your tool decides your project needs a library for file uploads, date formatting, or HTTP requests, it adds it to your package.json or requirements.txt and imports it in the generated code. This keeps the workflow smooth, but it introduces a risk most founders don't know about: slopsquatting.

What happens High Risk

The Cloud Security Alliance's April 2026 research found that 19.7% of AI-generated code samples contained at least one hallucinated package name — a package that doesn't actually exist. Worse, 43% of those hallucinated names reappeared consistently when the same prompts were repeated. Consistent hallucinations are predictable. Predictable names are registerable.

Attackers monitor which package names AI tools frequently hallucinate, then register malicious packages with those exact names on npm, PyPI, and other registries. When your AI tool suggests the package and your build system downloads it, you get malware instead of a library. The package might exfiltrate your environment variables, insert backdoors, or cryptomine using your server's resources — and you'd never know, because you didn't choose the package. The AI did.

What to do:

  • Review every dependency your AI tool adds — check it exists on the official registry (npmjs.com, pypi.org) before installing
  • Look at download counts, last publish date, and open issues — abandoned or suspicious packages are red flags
  • Run npm audit or safety check (Python) regularly to detect known vulnerabilities
  • Pin dependency versions in your lockfile so you're not silently pulling updates that might introduce vulnerabilities
  • Consider using --no-auto-commits (Aider) or reviewing dependency changes before they enter your codebase

Best Practice 5: Implement Authentication and Authorization — Don't Trust the AI

Authentication (who is this user?) and authorization (what are they allowed to do?) are the two most security-critical parts of any application. They're also the parts where AI tools most commonly cut corners — generating code that "works" for the logged-in user but doesn't properly check whether User A can access User B's data.

What happens High Risk

The most common pattern: an AI-generated API route accepts a user ID as a parameter and returns that user's data — without checking whether the person making the request is actually that user. This is called Broken Object Level Authorization (BOLA), and it's #1 on the OWASP API Security Top 10. It means anyone who's logged in can access anyone else's data by simply changing a number in the URL.

A 2025 study of Lovable-built apps found that 10.3% had Row Level Security bypass vulnerabilities across 303 endpoints in 170 projects. The Tea app, a well-known case study, leaked user DMs through broken access control logic that AI generated without review. These aren't hypothetical scenarios — they're documented incidents from real apps.

What to do:

  • For every API route that returns user-specific data, verify that the requester is authorized to see that specific data — not just that they're logged in
  • Never trust a user ID from the client — derive it from the authenticated session
  • Test manually: log in as User A, then try to access User B's data by changing the ID in the URL or request body. If it works, you have a BOLA vulnerability
  • Use your framework's built-in authorization features (Supabase RLS, NextAuth, Django permissions) rather than building custom checks

Best Practice 6: Scan Before You Ship — Every Time

The research is unanimous on this point: static analysis catches what manual review misses. SAST (Static Application Security Testing) tools scan your code for known vulnerability patterns — SQL injection, hardcoded secrets, missing authentication, vulnerable dependencies. SCA (Software Composition Analysis) tools check your dependencies against known vulnerability databases.

What happens Essential Practice

Orca Security's 2026 guidance is blunt: "Gate every merge with SAST and SCA in CI. Make the scan a required check, so a flaw caught at pull-request time never reaches the main branch." Cycode adds: "Scan all AI-generated code with SAST and SCA tools before it reaches a pull request. Prohibit AI-generated code in high-risk areas (authentication, encryption, payment processing) without mandatory human review."

The key insight: AI tools generate code faster than humans can review it. Automated scanning is the only practical way to keep up. A SAST scan takes minutes. Manual review of the same code takes hours. For founders who can't read code at all, a scan is the only option — and a plain-English interpretation of the scan results is what SecondRead provides.

What to do:

  • Run a SAST scan on your codebase before launch — tools like Semgrep, SonarQube, or CodeQL are free for open-source projects
  • Run an SCA scan to check dependencies — npm audit, safety check, or GitHub's Dependabot alerts
  • If you can't interpret the results yourself (most founders can't), get a plain-English audit that translates them into actionable findings
  • Make scanning a recurring practice, not a one-time check — every significant code change should trigger a new scan

Best Practice 7: Don't Let AI Touch Critical Security Code Unreviewed

Some parts of your application are more security-critical than others. Authentication flows, payment processing, encryption, access control, and session management are areas where a single mistake can compromise your entire application. AI tools can generate code for all of these — but that doesn't mean they should do it unsupervised.

What happens Critical

Cycode's 2026 guidance is explicit: "Prohibit AI-generated code in high-risk areas (authentication, encryption, payment processing) without mandatory human review." The reasoning is simple: these are the areas where AI tools' blind spots are most dangerous. A missing authorization check on a blog comment route is bad. A missing authorization check on a payment route is catastrophic.

Arnica's CISO guide adds: "The minimum viable compliance baseline for AI code security includes a documented AI coding tool inventory, a defined review gate before AI-generated code merges, evidence of security scanning at each gate, and an audit trail that ties each code artifact back to its originating tool and reviewer."

What to do:

  • Identify your critical security surfaces: authentication, authorization, payment, data access, encryption
  • These areas require expert review — either from a security professional or from a service like SecondRead that specialises in AI code audits
  • For non-critical areas (UI components, marketing pages, internal tools), AI-generated code is lower risk but should still be scanned
  • Keep a record of which parts of your codebase were AI-generated — you'll need this for compliance audits and for scoping future security reviews

Best Practice 8: Iterate Carefully — More AI Prompts Can Make Code Worse

Here's a finding that surprises most founders: iterating with AI doesn't always improve your code. In many cases, it makes security worse.

What happens Counterintuitive Risk

Arnica's 2026 research found that iterating with AI increases critical vulnerabilities by 37.6% instead of fixing existing flaws. Each round of AI-generated changes introduces new issues while partially addressing old ones — resulting in a codebase that's more complex, more fragile, and more vulnerable than the version before.

This happens because AI tools optimise for the specific request you make, not for the overall health of your codebase. When you ask "add a password reset feature," the tool generates code for that feature — but it might introduce a new vulnerability in the process (e.g., a reset token that doesn't expire, or a reset endpoint that leaks whether an email exists). Each iteration adds surface area. More surface area means more attack vectors.

What to do:

  • Be intentional about iterations — each change should address a specific need, not be a fishing expedition
  • After a round of AI changes, re-scan for security issues before moving on
  • Don't use AI to "fix" security issues it introduced — it often creates new ones in the process. Get human review or a specialised audit for security fixes
  • Track your codebase's security posture over time — if each iteration makes it worse, you need a different approach

Best Practice 9: Have a Vulnerability Response Plan Before You Need It

Security isn't a state you achieve — it's a practice you maintain. Even with all the best practices above, vulnerabilities will be found. Some will be discovered by you. Some will be discovered by users. Some will be discovered by attackers. The question isn't whether this will happen; it's whether you'll be ready when it does.

What to prepare Preparedness

The UK's Code of Practice for the Cyber Security of AI (2026) sets baseline expectations that are spreading to other jurisdictions: documented vulnerability disclosure processes, supply chain transparency, and evidence of security testing. PCI DSS 4.0 and SOC 2 Type II auditors are increasingly asking about AI code provenance and whether output undergoes security testing before production deployment.

Even if you're not subject to formal compliance requirements yet, having a plan means the difference between a minor incident and a major crisis. A found vulnerability that you patch in 24 hours is a footnote. The same vulnerability that sits unpatched for a month because nobody knows what to do is a headline.

What to do:

  • Have a process for receiving vulnerability reports — a security contact email (e.g., security@yourdomain.com) is the minimum
  • Know how to rotate credentials quickly — keep a list of all secrets your app uses and where each is stored
  • Have a way to deploy hotfixes quickly — if a critical vulnerability is found, you need to fix it in hours, not weeks
  • Consider a recurring audit schedule — code changes, and new vulnerabilities are discovered constantly. An audit at launch is good; quarterly audits are better

Best Practice 10: Get an Independent Audit Before Launch

You can run all the scans, checklists, and manual reviews above and still miss critical issues. Security is adversarial — attackers think creatively about ways to break your app that you wouldn't anticipate. An independent audit brings fresh eyes and specialised expertise that self-review can't match.

The case for independent review

Arnica's 2026 CISO guide recommends: "Treat AI suggestions as untrusted input. Require the same peer review and security gate coverage you would for any third-party code contribution." Checkmarx adds: "Without rigorous post-generation review, legacy vulnerabilities can slip into production environments undetected."

The key word is independent. The person who built the app — or the AI tool that generated it — has blind spots about its security. An external reviewer doesn't. They see the code for what it is, not for what it was intended to be.

For founders who can't read code, an independent audit serves a second purpose: translation. A security audit that outputs a list of CVE IDs and file:line references is useless if you don't know what those mean. You need findings translated into plain English: "your API accepts any input without checking it," "your database credentials are in your git history," "any logged-in user can access any other user's data." That translation is what makes an audit actionable for a non-technical founder.

The AI Code Security Checklist: Run This Before Launch

Before you ship your AI-built app, run through this checklist. Each item maps to a best practice above:

  1. ✅ Have you scanned for hardcoded secrets across your entire git history (not just current code)?
  2. ✅ Does every API route validate input against a schema before processing?
  3. ✅ Have you verified that every dependency the AI added actually exists on the official registry?
  4. ✅ Can User A access User B's data by changing an ID in the URL? (Test this manually.)
  5. ✅ Have you run a SAST scan (Semgrep, SonarQube, CodeQL) on your codebase?
  6. ✅ Have you run an SCA scan (npm audit, safety check) to check for vulnerable dependencies?
  7. ✅ Have authentication, payment, and access control code been reviewed by someone other than the AI?
  8. ✅ Do you have a security contact email and a plan for responding to vulnerability reports?
  9. ✅ Have you documented which parts of your codebase were AI-generated?
  10. ✅ Have you had an independent audit with plain-English findings?

If you can't confidently answer "yes" to all ten, your app isn't ready to launch. That's not a judgement — it's the reality of building with AI tools in 2026.
